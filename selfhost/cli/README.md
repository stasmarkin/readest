# readest CLI

Командная строка для selfhost-сервера Readest: посмотреть библиотеку, выгрузить заметки книги, залить новые книги, заменить книгу новой версией и удалить книгу так, что клиенты (macOS, Android, веб) получат это своим обычным синком — как будто всё сделано из приложения. Прогресс, заметки и настройки CLI не правит; `--replace` только переносит прогресс и статус старой строки на новую.

## Установка

Нужен Node 24 (TypeScript запускается напрямую, без `node_modules` и сборки).

```sh
ln -s "<чекаут>/selfhost/cli/readest.ts" ~/.local/bin/readest
readest --help
readest --version   # короткий sha чекаута
```

Симлинк обновляется вместе с чекаутом. Команде `notes` нужен подмодуль `packages/foliate-js` (из него берётся сравнение CFI, тем же приложение сортирует заметки). В голом клоне: `git submodule update --init -- packages/foliate-js`. Без подмодуля `notes` падает с этой подсказкой, остальные команды работают.

## Сервер и вход

Профиль сервера — ровно один источник:

- все три переменные `READEST_API_URL`, `READEST_SUPABASE_URL`, `READEST_ANON_KEY` (тестовый стек; разрешены `http` и разные origin);
- ни одной — тогда конфиг берётся из `${READEST_URL:-https://readest.stasmarkin.ru}/.well-known/readest-client-config.json`; адреса обязаны быть `https` и того же origin, что `READEST_URL`.

Частичный набор переменных — ошибка.

```sh
readest login --email me@example.com   # пароль спросит без эха или возьмёт из READEST_PASSWORD
readest whoami [--json]
readest logout
```

`whoami` проверяет сессию запросом к серверу, а не только по файлу: отозванный сервером токен, который не удалось обновить, — код 3. `whoami --json` печатает ровно `{"email", "userId", "server"}` (`server` — `apiBase` профиля), лок не берёт.

Пароль не сохраняется. Сессия лежит в `~/.config/readest-cli/session-<хост>-<хеш>.json` (файл 600, каталог 700), токен обновляется сам. Если обновить не удалось — код 3, нужен повторный `readest login`.

## Команды

```sh
readest books [--search S] [--json] [--expect-user ID]
readest notes <книга> [--format md|json] [--out FILE]
readest upload <файл…> [--group ПУТЬ] [--dry-run] [--allow-duplicate] [--expect-meta M] [--json] [--expect-user ID]
readest upload <файл> --replace <hash> [--resume] [--expect-meta M] [--json] [--expect-user ID]
readest delete <hash…> [--json] [--expect-user ID]
```

- `--expect-user ID` — userId, который видел вызывающий (например, из `whoami --json`). Если в профиле теперь сессия другого аккаунта — код 3, ничего не прочитано и не записано.

- `books` — таблица (hash7, формат, прогресс, `cloud`, группа, автор — название), новые сверху; `--json` — массив `{hash, metaHash, title, author, format, progress, readingStatus, groupName, uploadedAt, updatedAt}`. `--search` — подстрока без учёта регистра по названию, автору и группе.
- `notes` — `<книга>`: полный hash, префикс hash от 6 символов или часть названия; несколько совпадений — ошибка со списком кандидатов. По умолчанию Markdown в stdout по образцу экспорта приложения; `--out` перезаписывает файл.
- `upload` — EPUB, PDF, FB2, FBZ (`.fbz`, `.fb2.zip`, `.fb.zip`). MOBI/AZW3, CBZ, TXT заливаются из приложения. `--group "Фантастика/Лем"` кладёт новую (или оживлённую) книгу в группу; существующие книги CLI по группам не перекладывает. `--dry-run` показывает решение и ключи файлов, ничего не записывая. Дубль по `metaHash` пропускается без `--allow-duplicate`.

## upload из скриптов

- Никогда не спрашивает ввод.
- Коды выхода: 0 — все файлы залиты или пропущены; 1 — хотя бы один файл с ошибкой (в том числе перехваченный посреди запуска лок) или сбой всего запуска; 2 — ошибка использования; 3 — нужен вход (в том числе если за время запуска в профиле вошли под другим аккаунтом: запусти заново).
- `--json`: в stdout ровно один JSON-массив `{file, status, reason?, hash, title, group?, metaHash, uncertain?}` (`status`: `uploaded`, `reuploaded`, `revived`, `skipped`, `replaced`, `error`; у `skipped` `reason` — `already` или `duplicate` с `duplicateOf`; у `error` — текст ошибки). `metaHash` — у `uploaded`/`revived` значение записанной строки, у `already`/`reuploaded` — строки сервера (может быть `null`), у `duplicate` — файла. `uncertain: true` у `error` значит «исход неизвестен» (сеть, таймаут, 5xx, `sync not confirmed`, потерянный лок, сбой контрольного чтения после записи): повтори; без него ошибка относится к файлу. Предупреждения и диагностика — в stderr. При сбое всего запуска с кодом 1 в stdout — `[]`, ошибка — в stderr. При кодах 2 и 3 stdout пуст.
- Повтор безопасен (идемпотентен), его можно гонять в цикле до кода 0:
  - уже залитая книга — `skipped` (`already`), ничего не пишется;
  - после упавшей заливки файла (`PUT`) повтор продолжает под тем же ключом и тем же резервом места;
  - книга, когда-то удалённая из библиотеки, возвращается как `revived` с прежним прогрессом и заметками;
  - строка есть, а файла в хранилище нет — `reuploaded`;
  - `sync not confirmed` — непонятно, записалась ли строка: повтор либо найдёт её (`skipped: already`), либо допишет.
- `--group` меняет группу только у `uploaded` и `revived`; для `skipped` и `reuploaded` в stderr предупреждение, что группа не изменена.
- Параллельные `upload` и `delete` одного профиля идут по очереди (общий лок `~/.config/readest-cli/upload-<профиль>.lock`). Если лок перехватили посреди запуска, готовые результаты печатаются, текущий элемент — `error` с `uncertain`, остальные не обрабатываются, код 1.
- `--expect-meta M`: существующую строку того же hash (`already`, `revived`, `reuploaded`) CLI принимает, только если её `meta_hash` равен `M`; иначе `error` с `conflict: …` без записи. Без флага проверки нет.

## upload --replace

`readest upload <файл> --replace <oldHash> [--resume]` ставит новую версию книги вместо `oldHash`: ровно один файл; `--group`, `--dry-run`, `--allow-duplicate` с ним — код 2 (группа берётся у старой строки), `--resume` без `--replace` — тоже код 2.

1. Строки `oldHash` нет — `error` `replace target not found`. Строка удалена — `replace target deleted` (книгу удалил пользователь), если не передан `--resume`.
2. Hash файла равен `oldHash` — `error` `same hash`.
3. Новая книга заливается, дозаливается или оживляется (`step`: `uploaded`, `reuploaded`, `revived`; уже готовая — `already`) одной записью строки с полями старой: группа, `progress`, `readingStatus` (`finished` → `unread`), метки группы и статуса выше обеих строк. Дубль по `metaHash` против `oldHash` не считается; другая живая книга с тем же `metaHash` — `error` с `duplicateOf`. Ответ сервера сверяется с перенесёнными полями: расхождение — `error`, старая книга не трогается.
4. Старой строке ставится `deletedAt`, все её объекты в хранилище удаляются.

Результат — `replaced` с `hash`, `metaHash`, `replacedHash`, `step`, или `error`. Сбой на любом шаге после записи новой строки — `error` с `uncertain`. Повтор с `--resume` доводит замену и третью книгу не создаёт; если старая уже удалена, а новая живая с файлом, повтор только дочищает объекты старой и новую строку не переписывает.

## delete

`readest delete <hash…> [--json]` — все hash проверяются до любого запроса (невалидный — код 2). Для каждого: строке ставится `deletedAt` (если ещё не стоит), объекты хранилища с этим `book_hash` удаляются поштучно, затем список перечитывается — оставшийся объект даёт `error` (ответ 404 удаления не считается доказательством). Объекты ищутся и без строки: так убирается мусор оборванной заливки. `--json` — массив `{hash, status, reason?, uncertain?}`: `deleted`, `skipped` с `reason: missing` (ни строки, ни объектов), `error`. Коды и `[]` при сбое запуска — как у `upload`. Заметки и настройки книги остаются на сервере.

## Ограничения

- Книга появится на устройстве, только если в клиенте включён облачный синк Readest.
- Заметки — без заголовков глав: оглавление есть только в файле книги.
- `metaHash` EPUB/FB2 — свой разбор; клиент пересчитывает его при первом открытии книги. У PDF значение остаётся навсегда, а `/Info` читается только несжатый: при сжатом `/Info` или только XMP-метаданных расходится связь заметок между разными файлами одной книги и поиск дублей.
- Если на другом устройстве прогресс книги изменится в доли секунды между перечитыванием её строки и записью (`POST`), это изменение может быть перезаписано: у API нет условной записи.
- Резерв места после оборванной заливки файла занимает квоту, пока заливку не повторят.
- Упавшую обложку повтор не дозаливает: книга уже `skipped: already`.
- CLI рассчитан на selfhost-сервер на Node: библиотека читается одним ответом без `limit`. На развёртывания в Cloudflare Worker он не рассчитан — там большой ответ упрётся в лимиты воркера.
- Старые облачные файлы с пустым `book_hash` в таблице `files` CLI не видит и может залить книгу заново.
- `usage` в отказе по квоте от selfhost-сервера может быть 0: сервер берёт его из claim токена, если не посчитал сам.
- `--dry-run` для нескольких файлов не учитывает файлы, залитые раньше в этом же запуске: решение по каждому — как будто он первый.
- Тело `POST /api/sync` со строкой книги больше 900 KiB не отправляется (лимит сервера — 1 MiB): сначала отбрасывается `metadata.description` (с предупреждением), если и без него велико — ошибка файла до заливки.
- Если между хешированием и `PUT` исходный файл заменили другими байтами того же размера, CLI этого не заметит.
- `--replace` не переносит позицию чтения (конфиг книги): CFI старой версии указывали бы не туда. В библиотеке виден процент из `progress`.
- Заметки после `--replace` доезжают по общему `metaHash`, но их CFI указывают в старую версию: после правки текста выше выделения подсветка может сместиться или пропасть.
- Смена `title` или `author` меняет `metaHash`: заметки старой версии к новой не привязываются.
- `delete` и очистка старой книги в `--replace` не видят объекты с пустым `book_hash` (см. выше): такие файлы остаются в хранилище.
- Если другой клиент восстановит книгу между её tombstone и удалением объектов, CLI удалит и её файл: у API нет условного удаления.
- Если после сбоя `--replace` новую версию успели почитать, а старая ещё жива, `--resume` вернёт новой прогресс старой.
